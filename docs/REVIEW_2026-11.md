## 1. Summary

release-kit is small, readable and unusually well hardened for its size.
About 1,100 lines of dependency-free Node, four workflows, and 67 tests that include end-to-end runs against throwaway git repos.
The workflow hardening (SHA-pinned actions, read-only defaults, no `${{ }}` inside shell scripts) is enforced by tests, which most release tools do not do for themselves.

The most important findings:

1. **The OSV gate fails open when it is started through a symlink or a path with a space** (reproduced).
   `osv-gate.mjs` decides whether it is the main module with `import.meta.url === \`file://${process.argv[1]}\``, unlike every other script, which uses `isMain()` from `git.mjs`.
   Started as `node scripts/release-kit/osv-gate.mjs report.json` in this repo, where `scripts/release-kit` is a symlink into `template/`, it prints nothing and exits 0, even for a report with a malicious (`MAL-`) package.
   The same happens for any path with a space or another character that URL encoding changes.
   That means the kit's own weekly security scan can never fail today.
   Adopters in package and reusable mode run the gate from `$RUNNER_TEMP`, which has neither problem, so they are not affected on GitHub-hosted Linux runners.
2. **Package mode does not install on npm 12** (reproduced with npm 12.2.0).
   `npm install` of `github:n8watkins/release-kit#v2.1.0` stops with `EALLOWGIT` because npm 12 refuses git dependencies by default.
   The README quick start passes `--allow-git` only to the `npx` call, so its second step (`npm install`) fails on npm 12.
   Adding `allow-git=root` to the repo's `.npmrc` fixes it (reproduced).
   GitHub-hosted runners still ship an older npm with Node 22 and 24, which is why adopters' CI is green; this breaks the day the runner npm moves to 12.
   docs/HANDOFF.md already lists this as open problem 1, and it is still open.
3. **New kit files never reach adopters.**
   None of the 8 adopters has `security.yml`, the headline feature of v2.1.0, because Dependabot can bump pins but cannot add files.
   Four adopters (scribe, voicedock, portfolio-rank, tl-dw) are also still on v2.0.0 with two or three unmerged Dependabot PRs each.
4. **One kit release becomes two or three Dependabot PRs per repo**, one for the npm dev dependency and one per workflow file that pins the kit.
   Each PR runs the repo's full CI, and merging only some of them leaves the repo with the dev dependency and the workflows on different kit versions.
   Dependabot multi-ecosystem groups can make this one PR per repo (see section 2.6).
5. **The Release workflow's two jobs have no `timeout-minutes`**, so a hung `release:check` can run for GitHub's default of 360 minutes.
   That is free in a public repo and up to 18% of a month's free minutes in a private one.
6. **Docs drift:** STANDARD.md still says vendored is the default mode (package is), docs/HANDOFF.md says the latest release is v2.0.1 and lists piper-tts (now voicedock), and the README's reusable example pins v1.1.0.

## 2. Systematic review

### 2.1 Architecture

The kit has three layers.

- **Scripts** in `template/scripts/release-kit/`: `conventional.mjs` (parsing, linting, bump and plan logic, all pure functions), `git.mjs` (git helpers with careful argument handling), `notes.mjs`, `release.mjs`, `train.mjs`, `versions.mjs`, `protect.mjs`, `commit-msg.mjs` and `osv-gate.mjs`.
- **Workflows** in `template/.github/workflows/`, mirrored byte for byte in `.github/workflows/` so other repos can call them as reusable workflows, and thin callers in `reusable/`.
- **Installer**: `apply.mjs` writes or upgrades a repo, and `bin/release-kit.mjs` is the single command in package mode.

Strong points:

- The pure core (`conventional.mjs`) is cleanly separated from side effects, which is why it is easy to test.
- Reusable workflows fetch the scripts at `job.workflow_sha`, so the version pin in the caller decides every line of code that runs in CI.
  This is the right design and is subtle enough that most homegrown kits get it wrong.
- The release notes travel inside the annotated tag, so the GitHub Release always equals the `CHANGELOG.md` section, including a hand-edited one.
- `release.mjs --push` is transactional: `release:check` first, one atomic push of branch and tag, and an undo when the push is rejected.
- The release train is careful about the hard GitHub rules (the `GITHUB_TOKEN` starts no workflows, `workflow_dispatch` checks do not satisfy protection) and documents them where they matter.
- `.release.json` holds every per-repo choice, so re-running apply is a safe upgrade.

Weak points:

- Three install modes (package, reusable, vendored) triple the surface for a kit with 8 adopters, all in package mode.
  Reusable and vendored mode are only exercised by tests.
- The kit assumes npm everywhere: apply requires a `package.json`, and the workflows run `npm ci`.
  A pnpm, yarn or bun repo needs a second lock file, and a repo without `package.json` (a Python or Go project) cannot adopt it at all.
- There is no machine-readable output from apply, which a rollout bot or an admin page would need (what changed, which version, which warnings).
- The same "Fetch the release-kit scripts" and "Locate" steps are repeated in five jobs.
  A test keeps the copies identical, which is the right mitigation, but a composite action inside the kit would remove the duplication.

### 2.2 Code quality

The code is consistent, commented for intent rather than mechanics, and defensive in the right places: tag names and refs are validated before they reach git or a shell, `--end-of-options` is used on every user-supplied ref, git log output uses control-character separators and a 1 GB buffer, CRLF and byte-order marks are normalised.

Specific issues, most important first:

1. `osv-gate.mjs` main-module check (see Summary, item 1).
   Fix: use `isMain(import.meta.url)` from `git.mjs`, and make the workflow fail closed by checking that the gate printed its `OSV:` summary line.
   Add a test that runs the gate as a CLI through the `scripts/release-kit` symlink with a malicious report and expects exit 1.
2. `isBot()` matches on the author name (`[bot]$`, `^dependabot`, `^github-actions`).
   Anyone can set `user.name` to `dependabot` and skip the commit check and the notes.
   The check is about hygiene, not security, so this is acceptable, but it should be documented, and the CI check could match bot accounts by the noreply email domain instead.
3. Git's own revert messages (`Revert "feat: x"`) are exempt from the check and are not user-facing to the train, while the README and STANDARD.md say "a revert" triggers a release.
   Only the `revert:` type does.
   Either parse `Revert "<conventional header>"` or reword the docs.
4. The CI commit check runs on pull request commits and on pushes to main.
   With squash merges, the commit that lands on main gets the PR title as its header, and that title is only checked after it is already on main.
   A PR-title check (the `pull_request` event's `title`) would catch it before merge; n8builds already had a header-length failure of exactly this kind.
5. `release.yml`'s `verify` job checks out with persisted credentials while it runs `npm ci` and the repo's own `release:check` and `release:artifacts`.
   The token is read-only, so the risk is low, but every other job sets `persist-credentials: false` and this one should too.
6. `protect.mjs` adds a `DeployKey` bypass actor, which GitHub applies to every deploy key with write access, not only the train's key.
   The script is clear that it creates one key, but the README should say that any other write deploy key on the repo can also bypass main's ruleset.
7. apply treats any `core.hooksPath` other than `.githooks` as another hook manager, even when the folder does not exist, and then installs no hook (HANDOFF open problem 2, still open).
8. `bin/release-kit.mjs check` runs `git ls-remote` on every `release:check`, including inside the Release workflow.
   It is warn-only and has an 8 second timeout, but `RELEASE_KIT_OFFLINE` is undocumented.

### 2.3 Tests

`npm test` on Node 24.16.0: 67 tests, 66 pass, 0 fail, 1 skipped, in 25 seconds.
The skipped test is "applied workflows pass actionlint", which skips when actionlint is not installed locally; CI installs a checksum-verified actionlint, so it runs there.

What is covered well: commit parsing and linting, bumps and plans, version files (JSON, Cargo, npm locks, Tauri layouts), apply in every mode including husky and other hook managers, the release command end to end against a local bare remote, the train against a fake `gh`, protect against a fake API, workflow hardening rules, and the Node version detection step.

Gaps:

- No CLI test of `osv-gate.mjs`, which is how the fail-open bug went unnoticed: the unit tests import `gate()` directly.
- No test for `bin/release-kit.mjs`, including `check` and the dispatch to each script.
- No test that installs the kit as a git dependency with the current npm, which would have caught `EALLOWGIT`.
- No test runs on Windows, although `scribe` and `voicedock` are Windows apps whose contributors commit on Windows; the hook is a `sh` script that relies on Git for Windows' shell.
- No coverage report; `node --test --experimental-test-coverage` would give one for free.
- The skip of actionlint locally means a contributor can push a workflow that fails only in CI.
  Making the test fail when `CI` is set and actionlint is missing would turn a silent skip into a loud one.

### 2.4 Docs

The docs are written in plain, concrete language and explain the reasons behind each rule, which is rare and valuable.
They are, however, written for the owner: they start from "the n8 release standard" and "n8builds projects", repeat the same material across README.md, STANDARD.md, RELEASING.md and template/RELEASING.md, and the README mixes a quick start with a full reference.

| docs/HANDOFF.md | Latest release v2.0.1; adopters include piper-tts | v2.1.0; the repo is now voicedock |
| docs/HANDOFF.md | npm 12 and stale hooksPath are open | Both are still open |

### 2.5 Security posture

Strong:

- Every third-party action is pinned to a full commit SHA with the version in a comment, enforced by a test.
- Every workflow defaults to `contents: read`; only the publish job, the train's cut job and their callers get `contents: write` (and `actions: write` for the train), enforced by a test.
- No `${{ }}` expression is pasted into a shell script, enforced by a test, and tags reach the shell only after they match `vX.Y.Z`.
- Downloaded binaries (actionlint, OSV-Scanner) are pinned and checked against a SHA-256 before they run.
- Release artifacts get `SHA256SUMS.txt`, and the uploaded files are downloaded again and verified.
- The kit has no runtime dependencies, so its own supply chain is the Node standard library and git.
- The train never pushes an unchecked commit, and `protect.mjs` never leaves main unprotected while it swaps classic protection for a ruleset.

Weaker:

- The OSV gate can fail open (section 2.2, item 1).
- Adopters depend on a git tag, not a registry package, so there is no integrity hash beyond what `package-lock.json` records for the git commit, and no provenance.
  A tag can be moved by anyone with write access to release-kit; reusable callers can pin a SHA with `--kit-ref`, but package mode cannot.
- Release artifacts are checksummed but not signed and carry no build provenance attestation; GoReleaser and npm's trusted publishing both offer that today.
- The deploy key used by the train can bypass every rule on main, which is by design but makes `RELEASE_TRAIN_KEY` a high-value secret; it should live in a GitHub environment that only the train job can read.
- Dependabot PRs for the kit are opened daily with no cooldown, so a compromised kit tag would reach every adopter's PR queue within a day.

### 2.6 Apply and upgrade ergonomics

Adoption is genuinely about five minutes, and re-running apply is a safe upgrade that keeps every choice in `.release.json`.
The friction is entirely in upgrades:

1. A kit release creates 2 or 3 Dependabot PRs per repo.
   Across 8 repos that is up to 24 PRs, each running full CI, and they must all merge to avoid version skew.
   Dependabot's `multi-ecosystem-groups` key can put the npm and github-actions updates for release-kit into a single PR per repo.
   apply should write that, and also a `cooldown` of a day or two so a bad release can be pulled before it spreads.
2. Files the kit adds in a new release (security.yml in v2.1.0) need a manual `npx release-kit apply .` in every repo.
   This is the problem the rollout bot (section 6, phase 2) solves.
3. `release-kit check` warns only when the installed kit is behind; it does not say that kit-owned files are missing or out of date, so a repo can be "up to date" by version and still lack security.yml.
   A `release-kit doctor` that compares the repo with what apply would write would make drift visible.
4. The Dependabot commit prefix differs per repo (`ci:`, `build(deps):`, `chore(deps):`); apply could set `commit-message.prefix` so kit updates read the same everywhere.

### 2.7 Failure modes

| Failure | What happens | Recovery |
|---|---|---|
| Release run fails after the tag is pushed | No GitHub Release | Documented: rerun the Release workflow on the tag |
| Push of a release is rejected | Commit and tag are undone locally | Rerun after pulling |
| Train's checks fail, or main moves | Nothing is released, temp branch deleted | Next scheduled run |
| Train cannot delete its temp branch | Branch left behind, logged | Delete by hand |
| npm 12 on a developer machine | `npm install` fails with `EALLOWGIT` | `allow-git=root` in `.npmrc` (undocumented) |
| npm 12 on runners | Every adopter's `npm ci` fails | Same; not yet handled by apply |
| Stale `core.hooksPath` | No local hook, silently | CI still checks; HANDOFF open problem 2 |
| OSV gate run via symlink | Scan always passes | Fix in section 2.2 |
| OSV.dev or GitHub releases unreachable | Security scan fails red | Rerun; consider a retry |
| Partial Dependabot merge | Kit version skew, `release-kit check` warns | Merge the rest, or group the PRs |
| `release:check` hangs in Release | Runs up to 360 minutes | Add `timeout-minutes` |
| Security scan made a required check | PRs that touch no lockfile wait forever | Never require it; see section 4 |

## 3. Competitor comparison

Facts below were checked on 2026-11-02 against each project's GitHub repository (stars, last push, latest release) and documentation; see section 7.

### 3.1 The alternatives

**semantic-release** (24.2k stars, v25.0.9 released 2026-08-05, pushed 2026-10-31, MIT).
Fully automated: on every push to a release branch it derives the next version from Conventional Commits, writes notes, tags, publishes to npm and creates a GitHub Release, all through plugins.
Configured in `.releaserc`, `release.config.js` or `package.json`.
Monorepos are not supported first-party; the community uses `multi-semantic-release`, whose own README calls itself a hack.
It does not enforce commit messages; projects add commitlint and a hook manager.
Notes are developer-oriented changelog sections from `conventional-changelog` writers.
Supports release channels and prereleases.
Actively maintained and the most widely used.

**release-please** (7.7k stars, v17.11.2 released 2026-08-24, pushed 2026-11-02, Apache-2.0; the GitHub Action is at v5.0.0).
Keeps a "release PR" open that accumulates the next version and changelog; merging it tags and creates the GitHub Release.
Configured with `release-please-config.json` and `.release-please-manifest.json`, which is also how it supports monorepos.
It parses Conventional Commits but does not lint them, and its README says it does not publish to package managers.
`Release-As:` footers force a version, and a `BEGIN_COMMIT_OVERRIDE` block in a squash-merged PR body rewrites the message for the changelog.
It is what the deprecated standard-version recommends instead.

**changesets** (12.6k stars, `@changesets/cli` 3.0.3 released 2026-09-14, pushed 2026-11-01, MIT).
Contributors add a small Markdown "changeset" file per change saying which packages bump and how; `changeset version` consumes them into versions and changelogs, and `changesets/action` opens a "Version Packages" PR.
Monorepo-first, with dependency-aware bumps across workspace packages.
Does not use commit messages at all, so it neither needs nor enforces Conventional Commits.
Notes are written by people, which can read well but depends on discipline.

**release-it** (9.1k stars, 21.1.2 released 2026-10-30, MIT).
An interactive or CI command that bumps, commits, tags, pushes, publishes to npm and creates GitHub or GitLab releases.
Configured in `.release-it.json`; Conventional Commits and changelogs come from the `@release-it/conventional-changelog` plugin.
No commit enforcement, limited monorepo support (one run per package).

**git-cliff** (12.4k stars, v2.14.2 released 2026-09-18, pushed 2026-11-02, Apache-2.0).
A fast Rust changelog generator configured by `cliff.toml` with Tera templates and regex commit parsers, so notes can be shaped almost any way.
`--bumped-version` and `--bump` compute the next version, and `--include-path` scopes it to a monorepo package (an open issue, #648, covers multi-workspace bumps).
It does not tag, publish or enforce messages; it is a component, usually paired with other tooling.

**conventional-changelog** (8.5k stars, pushed 2026-11-01, ISC).
The family of parsers, presets and writers that semantic-release and many others build on; actively maintained, last release 2026-11-01.
**standard-version** is deprecated: its README says so and recommends release-please, or the `commit-and-tag-version` fork for those who cannot use GitHub Actions.
Its last release was v9.5.0 in May 2022.
`commit-and-tag-version` is maintained (v13.3.0, 2026-10-15, 660 stars).

**auto** by Intuit (2.5k stars, v11.3.6 released 2025-11-14, MIT).
Releases are driven by PR labels (`major`, `minor`, `patch`, `skip-release`) rather than commit messages; `auto shipit` versions, writes the changelog, publishes and creates the GitHub Release.
Configured in `.autorc`, with plugins for npm, monorepos (lerna-style), and more.
No commit enforcement; notes are grouped PR titles.
Still receives commits (latest 2026-06-18) but has not released in about a year.

**GoReleaser** (16.1k stars, v2.19.0 released 2026-10-22, MIT).
Not a direct competitor: it builds, packages and publishes binaries (Go first, plus other languages) from a tag, configured by `.goreleaser.yaml`.
Relevant as the benchmark for release supply-chain security: checksums, cosign signing, SBOMs and GitHub build-provenance attestations are documented and first-class.
Monorepo support is part of GoReleaser Pro.

**commitlint** (18.8k stars, v21.2.4, 2026-10-18) is the usual add-on that provides the commit-message enforcement the release tools above lack.

### 3.3 Where release-kit is genuinely different or better

1. **Enforced at commit time, out of the box.**
   Every alternative that reads commits trusts them; release-kit installs a hook and a CI check, so the history is clean before release time.
   Matching it elsewhere means adding and wiring commitlint and husky yourself.
2. **Written for agents.**
   apply maintains a marked block in AGENTS.md and CLAUDE.md with the commit and release rules, and the docs explain each rule in plain words an agent can follow.
   No competitor does this, and it matters when agents write most commits.
3. **Release notes for users, not developers.**
   The default New, Fixed, Faster, Safer style, the `Release-note:` trailer and `--summary` produce patch notes a visitor can read.
   release-please's commit override and changesets' human files can get there, but neither makes it the default.
4. **A release train that only ships when there is something to say.**
   Scheduled releases that skip quiet weeks, run the required checks on the exact release commit, and handle protected branches with a deploy key.
   semantic-release releases on every push and release-please on every release-PR merge; neither has "weekly, only if user-facing".
5. **Security in the same kit.**
   The weekly OSV scan that blocks malicious packages, plus hardened workflows whose rules are enforced by tests, plus zero runtime dependencies.
   No release tool in this list ships a dependency scan.

### 3.4 Where release-kit is behind

1. **No registry publishing:** it makes GitHub Releases and optional files; publishing to npm or another registry is left to the repo.
2. **No monorepo support:** one version per repo.
3. **npm only:** apply requires `package.json`, and the workflows need `package-lock.json`.
4. **Not on a registry itself:** package mode is a git dependency, which npm 12 blocks by default and which carries no provenance.
5. **No signing or provenance** for release artifacts, where GoReleaser and npm trusted publishing set the bar.
6. **No reviewable release PR:** release-please and changesets let a person read the next changelog in a PR before it ships; release-kit has `--dry-run` locally and a step summary in the train.
7. **No prerelease channels** (beta, next), which semantic-release and release-please support.
8. **Upgrades are manual beyond version pins**, and there is one maintainer.

## 4. CI lanes: running different checks for different changes

### 4.1 Should adopters run different checks for different change types?

Yes, with two guardrails.
A pull request that only edits Markdown, or only moves the release-kit pin from one version to the next, cannot break a browser test or a Windows build, and running them anyway costs real minutes in private repos and real waiting everywhere.
The guardrails are that the classification must fail toward running everything, and that pushes to main (and the release itself) always run the full suite, so a wrong classification can delay a failure but never ship one.

### 4.2 The pitfall to design around

When a workflow is skipped by a `paths`, `paths-ignore`, `branches` or commit-message filter, its checks are never created, and a branch rule that requires them leaves the PR "Waiting for status to be reported" forever.
GitHub's own troubleshooting page says not to use path or branch filters on a required workflow.
A job skipped by a job-level `if:` condition is different: it reports as skipped, which satisfies a required check.
release-kit's `security.yml` uses a `pull_request.paths` filter today, so it is safe only as long as nobody makes "Security scan" a required check.

### 4.3 Recommended shape

One workflow, three kinds of jobs:

1. **`changes`**: a classifier job that always runs, diffs the PR against its base, and outputs a `lane`.
2. **Lane jobs**: the repo's own checks, each with a job-level `if:` on the lane, never a workflow-level path filter.
3. **`result`**: one aggregate job with `if: always()` and `needs:` on everything, which fails if any needed job failed or was cancelled and passes when they succeeded or were skipped on purpose.
   This is the only required check.

n8builds-admin's `ci.yml` already uses exactly this pattern for docs-only changes ("What changed" and "CI result").
release-kit should generalise it and ship it.

### 4.4 The lanes

Lanes are ordered; a change gets the most demanding lane any of its files calls for.

| Lane | When | Runs |
|---|---|---|
| `docs` | Only `*.md`, `docs/**`, `LICENSE`, issue templates | Commit check, optional Markdown lint |
| `kit` | Only kit-owned changes: the `release-kit` entry in `devDependencies`, its entries in `package-lock.json`, kit-owned workflows (marked `release-kit`), `.github/dependabot.yml`, `RELEASING.md`, the release-kit block in AGENTS.md or CLAUDE.md, `.release.json` | Commit check and `release-kit verify` (below), about one minute |
| `deps-dev` | Only `devDependencies` and the lock file, and no package in the repo's `fullFor` list | Install, lint, types, unit tests, build; skips E2E and OS matrices |
| `full` | Anything else, any workflow the kit does not own, a missing base, the classifier's own config, or a classifier error | Everything |

What a kit-only update should run (`release-kit verify`, a new command):

1. `npm ci`, so the lock file and the git dependency still install (this is also where `EALLOWGIT` would show up).
2. `release-kit check` in offline mode, failing (not warning) when the dev dependency and the workflow pins disagree.
3. `release-kit doctor`: the kit-owned files match what apply would write for the pinned version.
4. actionlint on the kit-owned workflows.
5. `release-kit notes` and `npm run release -- --plan`, so the release scripts load and parse the repo's history.
6. `release.mjs --verify-tag` against the current version files.

It deliberately does not run the app's build or tests, because nothing the app ships changed.
The full suite still runs on the push to main after merge and on the next release.

### 4.5 Implementation sketch

- `template/scripts/release-kit/lanes.mjs`: a dependency-free classifier with a pure `classify(files, diffs, config)` function, so every rule is unit-tested.
  It reads `package.json` and `package-lock.json` at both the base and the head and compares them structurally, not as text, to tell "only the release-kit entry changed" apart from anything else.
- `.github/workflows/changes.yml` in the kit: a reusable workflow with outputs `lane`, `docs`, `kit`, `deps`, `full`, pinned like the others.
  It handles `pull_request`, `push` (always `full` on main), `merge_group` (base from the merge group), and `workflow_dispatch` (always `full`).
- `.release.json` `lanes`: optional `docs` and `fullFor` lists so a repo can widen the docs lane or force `full` for packages like `@playwright/test`, `typescript` or its bundler.
- apply writes an example `ci.yml` only for repos that have none, and otherwise prints the three-job pattern to copy, because a repo's CI is its own.
- `security.yml` becomes lane-aware: always triggered on pull requests, with a job-level `if:` on "a lock file changed", so it can safely be required.
- The `result` job is shipped as a tiny reusable piece (or documented snippet) so every repo names its required check the same way, for example `CI result`.

## 5. GitHub Actions minutes

### 5.1 The rules

Standard GitHub-hosted runners are free in public repositories.
Private repositories on GitHub Free get 2,000 minutes a month for the account (personal or free organization), after which usage is billed if a payment method and budget allow it, or workflows stop.
GitHub rounds each job's time up to a whole minute, so many small jobs cost more than their wall time suggests.
Dependabot's own update jobs are free, but the CI runs its PRs trigger are billed like any other run in a private repo.

### 5.2 release-kit's own workflows

release-kit is public, so its CI, commit check, security scan and releases cost nothing.

### 5.3 The kit's workflows inside a private adopter

Only n8builds-admin is private among the 8 adopters, and it bills to the personal n8watkins account.
Measured on its last 10 runs of each workflow (billed minutes, rounded per job):

| Workflow | Billed minutes per run | Runs |
|---|---|---|
| Commit messages (kit) | about 1.1 | Every PR push and every push to main |
| CI (repo's own) | about 6 | Every PR push and every push to main |
| Release (kit) | estimated 4 to 6 (verify runs the full `release:check`) plus 1 for publish; no run yet to measure | Per release |
| Security scan (kit, once adopted) | about 1 | Weekly, plus every PR that changes a lock file |

In its busiest recent stretch (100 runs between 2026-10-28 and 2026-11-02) that was roughly 290 billed minutes in six days, almost all from CI.
The kit's own share is small: the commit check costs about 1 minute per push, and the security scan would add about 5 minutes a month plus 1 per Dependabot lock-file PR.
The expensive part of a kit release is indirect: 2 or 3 Dependabot PRs, each running the full 6-minute CI and the commit check, often twice after rebases, which is 20 to 40 minutes per kit release in this one repo.
The `kit` lane cuts that to about 2 minutes per PR, and grouping the Dependabot updates cuts the number of PRs to one.

### 5.4 Monitoring

The Minutes page in n8builds-admin (`app/(dashboard)/minutes`) reads GitHub's enhanced billing usage report for the current month: `GET /organizations/Appturnity/settings/billing/usage` for the Appturnity org and `GET /users/n8watkins/settings/billing/usage` for the personal account, summing `actions` items with unit `minutes` and grouping them by repository.
Two problems:

1. The personal panel needs a token with the "Plan: read" account permission, and GitHub answers 404 without it; with the current setup the panel shows "needs permission".
2. Its copy says "The n8builds repos are public, so they use none of it", but n8builds-admin itself is private and its runs are billed to that account.

Recommendations:

- Grant the dashboard token "Plan: read" so the personal panel shows real numbers, and correct its copy to name n8builds-admin as the private repo that uses them.
- Add a per-workflow breakdown for n8builds-admin from the Actions API (`/actions/runs` and `/actions/runs/{id}/jobs`, rounding each job up), so the page can show what the kit's workflows cost versus the repo's own CI.
- Show a projection (minutes so far divided by days elapsed, times days in the month) and warn at 70% projected, not only at 70% used.
- Set a $0 or small Actions budget on the personal account so a runaway job cannot bill silently, and add `timeout-minutes` to every kit job (Release lacks them today).

## 6. Roadmap

Effort is for one experienced developer working with an agent, including tests and docs.

### Phase 0: fix what is broken (1 day)

- Fix the OSV gate main-module check, fail closed, and add a CLI test through the symlink.
- Handle npm 12: apply writes `allow-git=root` to `.npmrc` in package mode, the README says so, and a test installs the kit as a git dependency.
- Add `timeout-minutes` to the Release workflow's jobs and `persist-credentials: false` to `verify`.
- Fix the stale `core.hooksPath` case in apply (warn and install when the folder does not exist).
- Correct the stale docs in section 2.4 and refresh docs/HANDOFF.md.

### Phase 1: one PR per kit release (half a day)

- apply writes a Dependabot `multi-ecosystem-groups` entry for release-kit, a `cooldown`, and a consistent commit prefix.
- `release-kit check` fails in CI (warns locally) when the pins disagree.

### Phase 2: CI lanes (2 to 3 days)

- `lanes.mjs`, the reusable `changes.yml`, `release-kit verify` and `release-kit doctor`, as designed in section 4.
- Make `security.yml` lane-aware so it can be required.
- Migrate n8builds-admin first (it already has the pattern), then the repos with expensive CI (scribe's OS matrix, open-ping's Android build, n8builds-web's browser tests).

### Phase 3: the rollout bot (3 to 4 days)

- A GitHub App, "release-kit bot", with only `contents: write`, `pull_requests: write`, `workflows: write` (needed to change files in `.github/workflows/`) and `metadata: read`, installed on the adopter repos only.
- `adopters.json` in release-kit lists each repo, its default branch and its merge policy.
- `rollout.yml` runs on `release: published` and on demand: a matrix over adopters, each job minting a token scoped to that one repo with `actions/create-github-app-token`, running `npx release-kit@<tag> apply .`, updating the lock file, and opening or updating a single PR from the branch `release-kit/update` whose body is the release's notes plus apply's output.
- apply gets a `--json` report so the PR body and the status page can say exactly what changed.
- Waves: release-kit's own canary repo first, then the public repos, then n8builds-admin, with a pause to stop the rollout if the canary goes red.
- Dependabot stops watching release-kit once the bot is live, so there is one source of kit PRs, not two.
- PRs opened with an App token trigger CI normally, unlike PRs opened with `GITHUB_TOKEN`.

### Phase 4: auto-merge policy (1 day)

- Auto-merge only PRs whose lane is `kit` and whose version change is a minor or patch; a major kit release always waits for a person.
- GitHub's auto-merge needs a protected branch with a required check, and branch protection is not available for private repos on GitHub Free, so n8builds-admin cannot use it.
  For repos like that, the bot waits for the checks itself and merges only when every check passed, or leaves the PR for the owner; the policy lives in `adopters.json`.
- Each adopter enables "Allow auto-merge" and requires the single `CI result` check, which `protect.mjs` can set up.

### Phase 5: admin tracking page (1 to 2 days)

- A "Release kit" page in n8builds-admin that reads, per tracked repo: the `release-kit` version in `package.json`, the version each kit workflow pins, whether `security.yml` and the other kit files are present, the open rollout PR and its checks, and the latest GitHub Release.
- Computed from GitHub directly, so there is no second source of truth to keep in sync.
- Flags skew (pins disagree), drift (missing kit files), stuck PRs, and the security scan's last result.

### Phase 6: docs, README and a comparison page (1 to 2 days)

- README rewrite for people who are not the owner (a draft is in this PR).
- One reference document for options and `.release.json`, replacing the overlap between README.md, STANDARD.md and RELEASING.md.
- A public comparison page with the table in section 3.2, dated and sourced, and refreshed each quarter.

### Phase 7: catch up where competitors lead (each 1 to 3 days)

- Publish release-kit to npm with trusted publishing and provenance, which also removes the git-dependency problems.
- Build-provenance attestations (`actions/attest-build-provenance`) for release artifacts.
- A PR-title check, and a PR comment that previews the release notes a merge would add.
- pnpm, yarn and bun support in the workflows.
- Prerelease tags (`v1.2.0-beta.1`) for repos that want them.
- Windows CI for the hook, and a coverage report.
- Monorepo support only if an adopter needs it; it is the largest item and the least needed today.
